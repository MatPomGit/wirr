Jak rozpocząć laboratoria WiRR

Laboratoria wykonujesz samodzielnie. Każdy student prowadzi własny projekt Unity, wykonuje własne pomiary i wysyła własny raport. Wszystkie materiały przeznaczone dla studentów są publikowane w repozytorium KIA-students/wirr.

Pakiet WiRR przygotowuje środowisko, instaluje wymagane zależności, udostępnia materiały startowe, pomaga zweryfikować konfigurację i obsługuje raportowanie. Nie wykonuje ocenianych zadań za studenta.

Konfiguracja kursu: Unity 6000.6.x. Pakiet instaluj z gałęzi main, dzięki czemu instrukcja nie zależy od numeru konkretnego wydania.

1. Przygotowanie przed pierwszym laboratorium

  1. Zainstaluj Unity Hub oraz wskazaną wersję Unity 6000.6.x. Dla projektu wybierz szablon Universal 3D (URP).
  2. Zainstaluj Git i sprawdź w terminalu git --version. Po instalacji Git uruchom ponownie Unity Hub.
  3. Zaloguj się do GitHub. Repozytorium kursu dla studentów to KIA-students/wirr. Do wysłania raportu wymagane jest lokalne uwierzytelnienie Git, np. przez Git Credential Manager albo SSH.
  4. Opcjonalnie zainstaluj i zaloguj GitHub CLI. Polecenie gh auth status powinno potwierdzić logowanie. Dzięki temu pakiet może automatycznie utworzyć Pull Request po wysłaniu raportu.
git --version
gh --version
gh auth status

2. Instalacja najnowszej wersji pakietu WiRR

  1. W Unity otwórz Window → Package Manager (w niektórych układach: Window → Package Management → Package Manager).
  2. Kliknij +, następnie Install package from git URL… / Add package from git URL….
  3. Aby zainstalować bieżącą wersję pakietu, wklej poniższy adres i wybierz Install / Add.
https://github.com/KIA-students/wirr.git#main

Używaj dokładnie adresu z #main. Wskazuje on bieżącą wersję pakietu publikowaną dla studentów w KIA-students/wirr. Nie dopisuj numeru wersji ani ?path=Project~.

Po instalacji powinny być widoczne WiRR Course Toolkit w Package Manager oraz menu WiRR w edytorze.

3. Schemat pracy na każdym laboratorium

  1. Otwórz WiRR → Narzędzia kursu i wybierz właściwe laboratorium.
  2. Uruchom Zainstaluj / napraw zależności laboratorium. Zaczekaj na zakończenie instalacji i kompilacji.
  3. Zaimportuj oficjalne próbki Unity, jeżeli są wymagane, oraz próbkę WiRR. Pakiet utworzy przestrzeń roboczą Assets/WiRR/LabXX.
  4. Użyj Utwórz / napraw aktywną scenę, zapisz scenę i uruchom Sprawdź konfigurację laboratorium.
  5. W sekcji Zadania laboratoryjne wykonuj czynności w kolejności. Nie traktuj generatorów prefabów, przykładów XR/MR/AR ani materiałów demonstracyjnych jako gotowego rozwiązania ocenianego zadania.
  6. Dla każdego punktu kontrolnego wykonaj wymagany pomiar lub test i od razu zapisz wynik w formularzu raportu. Nie odkładaj odtwarzania danych pomiarowych na koniec zajęć.
  7. Po zakończeniu pracy zapisz projekt, uzupełnij własny raport, wybierz Sprawdź raport, a następnie Wyślij raport.

4. Punkty kontrolne i zakres wykonania

Laboratoria są podzielone na kolejne etapy 3.0 → 3.5 → 4.0 → 4.5 → 5.0. Etapy są sekwencyjne: wyższy etap zakłada poprawne wykonanie wymaganych elementów wcześniejszych.

Minimum do wysłania

Kompletny etap 3.0, dane studenta oraz wszystkie wymagane pomiary i tabele tego etapu. Dopiero wtedy przycisk wysyłania raportu staje się aktywny.

Etapy rozszerzone

Etapy 3.5–5.0 są opcjonalne. Wypełniaj je tylko wtedy, gdy faktycznie wykonałeś odpowiadające im zadania, pomiary i analizę.

Samo uruchomienie sceny lub uzyskanie poprawnego efektu wizualnego nie zastępuje pomiaru. W raporcie powinny znaleźć się rzeczywiste wyniki, warunki eksperymentu i krótki wniosek wynikający z obserwacji.

5. Raport indywidualny

  1. Otwórz WiRR → Raporty → Formularz raportu laboratoryjnego.
  2. Wybierz numer laboratorium. Praca jest indywidualna. Podaj identyfikator studenta oraz dokładnie jeden numer indeksu. Nie wpisuj imienia ani nazwiska.
  3. Uzupełniaj tabele danych surowych i pola opisowe na podstawie rzeczywistych pomiarów. Wartości jednoznacznie wynikające z danych, np. wybrane mediany, sumy, R=P×S lub statystyki RTT, są obliczane automatycznie.
  4. Szkic jest automatycznie zapisywany lokalnie w Library/WiRRReports. Folder Library jest lokalnym katalogiem projektu, nie częścią repozytorium studenta.
  5. Użyj Sprawdź kompletność raportu. Popraw wszystkie braki etapu, który chcesz zakończyć.
  6. Użyj Wyślij raport. Finalny raport ma format JSON zgodny ze schematem wirr-report/1.0.

Ścieżka oddania: Raport → Sprawdź → Wyślij → GitHub → walidacja CI → prowadzący. Raport nie jest wysyłany e-mailem, przez Teams ani Moodle, chyba że prowadzący wyraźnie wskaże inaczej.

Prywatność: aktualna wersja WiRR Reports wysyła treść raportu i dane identyfikujące zgłoszenie. Nie dołącza historii pracy w Unity, danych o systemie lub GPU, listy modyfikowanych plików ani telemetryki aktywności.

6. Gdzie trafia raport

  1. Raport trafia do repozytorium KIA-students/wirr jako plik students/reports/<student>/lab-XX/<submissionId>.json.
  2. Tworzona jest osobna gałąź w postaci report/<student>/labXX-<timestamp> i wykonywany jest push do repozytorium kursu.
  3. Jeżeli dostępny jest zalogowany gh, Pull Request może zostać utworzony automatycznie. Bez gh gałąź nadal jest wysyłana, a Pull Request należy utworzyć ręcznie.
  4. CI wykonuje kontrolę techniczną raportu, np. sprawdza schemat, numer laboratorium, identyfikator studenta i poprawność numeru indeksu. CI nie wystawia oceny merytorycznej.
  5. Ocena merytoryczna i zatwierdzenie wykonania laboratorium należą do prowadzącego.

7. Zasady pracy z projektem

  • Pracuj we własnych plikach w Assets/WiRR/LabXX. Nie edytuj zawartości Library/PackageCache.
  • Nie umieszczaj własnych rozwiązań w katalogach generowanych, jeżeli narzędzie informuje, że mogą zostać odtworzone lub nadpisane.
  • Przed aktualizacją pakietu zapisz i zacommituj własną pracę. Ponowny import próbki może nadpisać jej pierwotną zawartość.
  • Nie zmieniaj warunków testu po zobaczeniu wyniku. Zapisuj jednostki, konfigurację eksperymentu i wartości odniesienia.
  • Wynik, zrzut ekranu lub obserwacja bez kontekstu nie są pełnym dowodem. Powinno być wiadomo, co zmierzono, w jakich warunkach i jaki wniosek z tego wynika.

8. Gdy import lub raportowanie nie działa

  • Git nie został znaleziony: sprawdź git --version, dostępność Git w PATH i uruchom ponownie Unity Hub.
  • Nie znaleziono package.json: użyj adresu Git repozytorium, a nie adresu strony GitHub. Użyj URL z #main.
  • Brak menu WiRR: poczekaj na kompilację, otwórz Console i usuń pierwszy czerwony błąd. Sprawdź wersję Unity.
  • Brak sceny lub materiałów: zaimportuj próbkę wybranego laboratorium i użyj Utwórz / napraw aktywną scenę.
  • Przycisk „Wyślij raport” jest nieaktywny: uzupełnij dane studenta, wymagane pola etapu 3.0 oraz wymagane tabele pomiarowe, następnie ponownie sprawdź kompletność.
  • Push raportu nie działa: sprawdź lokalne logowanie GitHub oraz prawo zapisu do repozytorium kursu. Jeżeli automatyczne utworzenie PR nie działa, sprawdź gh auth status lub utwórz PR ręcznie z wysłanej gałęzi.
  • Aktualizacja pakietu: przed aktualizacją zapisz pracę w Git. Jeśli projekt utrzymuje starszy commit, usuń pakiet WiRR i dodaj ponownie URL z #main, a następnie ponów walidację laboratorium.

WiRR WebSim

Lokalny backend ROS 2 dla cyfrowego bliźniaka robota. Kontener generuje rzeczywiste komunikaty JointState, a Unity odbiera je przez rosbridge WebSocket.

W Lab 06 WebSim jest alternatywą dla Gazebo: ten backend generuje sygnał ROS 2, ale nie oblicza dynamiki ani kolizji w Gazebo. Klasyczny wariant Gazebo + ROS 2 jest odrębną ścieżką ćwiczenia.

Co działa

Oddzielne sesje studentów, RRBot 2R i WiRR Arm 3R, stan LIVE/STALE, ruchy A–C, Home i Reset.

Gdzie działa

Na komputerze studenta lub serwerze w tej samej sieci. Nie jest to serwer chmurowy: GitHub Pages publikuje wyłącznie tę instrukcję.

Przygotowanie

Potrzebujesz dostępu do repozytorium, terminala oraz Docker Desktop (Windows/macOS) albo Docker Engine z wtyczką Compose (Linux). Na komputerze z Unity nie trzeba instalować ROS 2 ani Gazebo.

docker --version
docker compose version

Oba polecenia powinny zwrócić wersję narzędzia. Jeśli nie zwracają, dokończ instalację Dockera i uruchom ponownie terminal.

Uruchomienie krok po kroku

  1. Pobierz kod. Sklonuj repozytorium albo przejdź do już pobranej kopii projektu.
  2. Wejdź do katalogu backendu. W tym katalogu znajduje się plik compose.yaml.
  3. Zbuduj i uruchom WebSim. Pierwsze uruchomienie może chwilę potrwać, ponieważ Docker pobiera obraz ROS 2.
  4. Poczekaj na gotowość. W logu musi pojawić się komunikat READY: WiRR WebSim ROS 2 signal generator. Pozostaw ten terminal otwarty przez całe ćwiczenie.
  5. Sprawdź topiki. W drugim terminalu wykonaj polecenie kontrolne. Na liście powinien być co najmniej /wirr/status.
git clone https://github.com/KIA-students/wirr.git
cd wirr/WebSim~
docker compose up --build

# drugi terminal, ten sam katalog
docker compose exec websim bash -lc 'source /opt/ros/jazzy/setup.bash && ros2 topic list'

Unity na tym samym komputerze

W WiRR → Narzędzia kursu → Lab 06 wybierz WebSim i wpisz adres:

ws://127.0.0.1:9090

Unity na innym komputerze

Ustal adres IPv4 komputera z Dockerem, otwórz na nim port TCP 9090 w zaporze i użyj:

ws://ADRES_IP_SERWERA:9090

Konfiguracja i wykonanie w Unity

  1. Otwórz WiRR → Narzędzia kursu, wybierz Lab 06, zainstaluj lub napraw zależności i użyj Utwórz / napraw aktywną scenę.
  2. Wybierz topologię WebSim. Wklej właściwy adres WebSocket: lokalny albo adres komputera-serwera z LAN.
  3. Wpisz kod swojej sesji: 3–12 znaków A–Z, cyfr, _ lub -. Wybierz RRBot 2R albo WiRR Arm 3R.
  4. Kliknij Utwórz / napraw model WebSim, aby utworzyć albo naprawić obiekt robota w scenie.
  5. Uruchom Play Mode, a następnie kliknij Połącz. Stan powinien przejść do LIVE.
  6. Wykonaj Ruch A, Ruch B, Ruch C, Pozycja początkowa i Resetuj. Obserwuj zmianę przegubów i zapisz wyniki do sprawozdania.

Ruch w Unity musi wynikać z topiku /wirr/<SESSION>/joint_states, a nie z lokalnej animacji klienta.

/wirr/<SESSION>/joint_states   sensor_msgs/msg/JointState, 30 Hz
/wirr/<SESSION>/command        std_msgs/msg/String
/wirr/<SESSION>/status         std_msgs/msg/String
/clock                         rosgraph_msgs/msg/Clock

Gdy coś nie działa

  1. Brak połączenia / ERROR. Sprawdź, czy docker compose ps pokazuje działający kontener, czy adres w Unity zaczyna się od ws:// oraz czy port 9090 nie jest blokowany przez zaporę.
  2. Połączenie przez LAN nie działa. Użyj adresu IPv4 komputera z Dockerem, nie 127.0.0.1; oba komputery muszą być w tej samej sieci.
  3. Stan STALE. Podejrzyj logi. Jeśli nie ma komunikatu READY, zatrzymaj i uruchom backend ponownie.
  4. Brak modelu lub przycisków. W Course Toolkit wykonaj ponownie instalację zależności oraz Utwórz / napraw aktywną scenę, potem utwórz cyfrowego bliźniaka.
docker compose logs -f
docker compose down
docker compose up --build

Zakończenie pracy

Po zapisaniu wyników zatrzymaj backend. Przy kolejnym ćwiczeniu uruchom go ponownie z tego samego katalogu.

docker compose down

Bezpieczeństwo: nie wystawiaj portu 9090 do Internetu. Jeśli potrzebujesz połączenia spoza LAN, użyj odrębnego reverse proxy z TLS/WSS i kontrolą dostępu.

Komfort w XR · Pomiar przed i po ekspozycji

Kwestionariusz SSQ

Oceń aktualne nasilenie każdego z 16 objawów: 0: brak, 1: niewielkie, 2: umiarkowane, 3: silne. Najpierw wykonaj pomiar przed ekspozycją, następnie po jej zakończeniu. Nie zakładaj, że wynik początkowy wynosi zero.

W razie dyskomfortu przerwij ekspozycję i poinformuj prowadzącego. SSQ opisuje nasilenie objawów; nie jest diagnozą ani zgodą na kontynuowanie ćwiczenia.

Polskie opisy są tłumaczeniem roboczym do dydaktyki, nie zwalidowaną polską adaptacją. Odpowiedzi pozostają tylko w pamięci tej karty przeglądarki; odświeżenie je usuwa. Pobierz wyniki przed zamknięciem strony. Nie podawaj danych osobowych.

Jak liczymy wynik?

Każda podskala jest sumą wskazanych odpowiedzi pomnożoną przez wagę. Numeracja odpowiada kolejności pytań powyżej.

  • N: nudności: (1 + 6 + 7 + 8 + 9 + 15 + 16) × 9,54.
  • O: objawy okulomotoryczne: (1 + 2 + 3 + 4 + 5 + 9 + 11) × 7,58.
  • D: dezorientacja: (5 + 8 + 10 + 11 + 12 + 13 + 14) × 13,92.
  • TS: wynik całkowity: suma wszystkich 16 odpowiedzi, każdej liczonej raz, × 3,74.

TS nie jest sumą ważonych podskal. Wyniki nie są procentami; większa wartość oznacza większe zgłoszone nasilenie. Nie stosujemy uniwersalnych progów diagnostycznych ani automatycznej klasyfikacji „bezpiecznie/niebezpiecznie”. Różnica Δ = po − przed może być ujemna; interpretuj ją razem z oboma pomiarami i warunkami ekspozycji.

Źródło: Kennedy, Lane, Berbaum i Lilienthal (1993), Simulator Sickness Questionnaire: An Enhanced Method for Quantifying Simulator Sickness, 3(3), 203–220.
